# 可信插件：安装、授权与安全边界

> [!WARNING]
> 这是有迁移要求的重大安全变更。升级前请先阅读 [可信插件升级指南](./UPGRADING_PLUGIN_TRUST.md)：旧插件首次需重新批准，Docker 必须持久化 `/app/.private`，已有密钥应在删除旧容器之前迁出备份。

## 信任模型

本项目采用 **管理员批准的可信插件模式**，不再全面禁用用户 JavaScript 插件，也不要求 Docker。

`src/plugins-user/<id>/index.js` 只有在管理员明确授权后才会导入。**批准插件等同于授权它以服务进程的权限运行**：插件能读取配置和密钥、修改文件、访问网络、执行命令、修改进程状态。只安装自己编写或已经审查、信任的插件。

管理员会话本身仍是高权限凭据，必须妥善保护。启用接口的再次输入密码是额外确认，不代表把持有管理员会话的人降为低权限用户，也不替代对其他管理接口的权限审查。

这不是恶意代码沙箱。原有基于调用栈的全局 fs/process/network 猴补丁已移除：它们既会误拦合法插件，又无法可靠限制恶意 JS。源码中的进程执行、隧道等正则匹配只产生审计提示，不再当作执行禁令或安全证明。插件报错、超时或禁用也不能撤销已经执行的代码、定时器或其他副作用。

`src/plugins/*` 仍是随服务部署的可信主机代码。上传接口不能覆盖内置插件，也不会将用户插件自动提升为内置插件。

## 在管理界面安装自己的插件

1. 打包整个插件目录，包含 `index.js` 和所需的本地模块、资源；导出的 `name` 必须与插件 ID 一致。
2. 登录后上传 ZIP。安装阶段只解压和登记，**不导入 JS**，新插件默认禁用。也可在本机手动部署到 `src/plugins-user/<id>/` 后重启发现它。
3. 刷新插件列表，点击启用。弹窗展示当前包的 SHA-256、服务权限风险说明，以及必须勾选的信任授权。
4. 确认文件与来源，勾选授权并输入当前管理员密码。服务端同时校验密码、明确授权和包哈希，成功初始化后才保存批准记录与启用状态。
5. 重启时，已批准、文件未变化且 `enabled:true` 的插件会自动加载，无需每次重启重新输入密码。

禁用不要求再次输入密码；手动重新启用仍需再次验证密码和确认授权。版本、说明和路由等 JS 元信息只在批准后读取，避免为了展示列表而提前执行代码。插件若调用管理器的 `getPluginList()`，现在需要 `await`，因为列表会异步计算包哈希。

## 插件管理页面调用 API

旧版插件页面若直接使用未认证的 `fetch('/api/...')`，升级后会返回 401，必须迁移。完整受影响范围、四种请求方法、打包重批和排查步骤见 [自定义插件管理页面鉴权迁移指南](./PLUGIN_PAGE_AUTH_MIGRATION.md)。

插件 HTML 页面与管理后台同源，但浏览器不会自动把 `localStorage` 中的管理员 token 添加到 `fetch()`。私有插件路由默认要求管理员会话，因此直接 `fetch('/api/my-plugin')` 会得到 401。

管理页面应使用内置的认证客户端；不要把 token 放进 URL、HTML 或插件配置：

```html
<script type="module">
  import { createPluginApi } from '/app/plugin-page-api.js';
  const api = createPluginApi('/my-plugin');

  const state = await api.get();
  await api.put({ config: state.config });
  // 子路径示例：await api.post({ value: 1 }, '/action');
</script>
```

客户端从现有管理登录状态读取 token，添加 `Authorization: Bearer ...`；没有会话或服务端返回 401 时会清理失效状态并转到登录页。服务端鉴权不能因页面来自插件而跳过。用户自有 Key 的公开业务页面应像 Potluck 一样通过经过审查的显式公共路由和自身 Key 鉴权实现，不能复用管理页面规则。

插件包内 HTML/JS 的任何变化都会改变包哈希。已经批准的插件修改页面后，刷新列表会显示需要重新批准；若当前进程已加载旧包，按提示先重启，再审查并批准新哈希。项目中的 IP 节点代理页面已按此方式迁移，可作为参考。

## 内容批准与更新

- SHA-256 覆盖插件目录内的文件名和完整文件内容，包括入口、依赖、配置及静态资源；不是仅检查 `index.js`，也不依赖修改时间或文件大小。
- 包不能包含符号链接、硬链接或特殊文件；检查沿用 1000 个文件、20 MiB 总内容限制。
- 批准记录保存在 `configs/plugins.json` 的 `approval` 中：`version:2`、`mode:"admin-approved"`、`sha256`、`approvedAt` 和服务器 HMAC `signature`。签名绑定插件 ID、哈希及批准时间，不能靠修改 JSON 或复制其他插件的批准记录伪造。不保存本次确认的管理员密码。
- 签名密钥由服务自动生成，保存在 `.private/plugin-approval.key`，不在可导出的 `configs/` 内，也不会写入镜像或 Git。只有真正批准插件时才创建密钥；验证时不会悄悄生成或替换密钥。请持久化并单独安全备份 `.private/`。随附的 Compose 文件已增加此挂载；自定义容器部署也应挂载 `/app/.private`。密钥丢失、损坏或被替换后，旧批准不会继续生效。丢失时可重新批准以生成新密钥；损坏时需先在主机上恢复或移走损坏文件，再重新批准，服务不会静默覆盖损坏密钥。
- 新版 tarball 在线升级器显式保留 `.private/`，也拒绝从更新包导入或替换这一路径的密钥（含大小写别名）；新版内置 Git 升级器在 checkout 前拒绝根目录跟踪 `.private` 的目标版本，正常更新保留本机私有状态。首次跨版本升级仍要先备份，因为执行首次升级的可能还是旧版升级器。此保护不代替 Docker 持久化挂载。
- **旧的 `enabled:true` 不代表批准。** 升级后的首次启动会禁用缺少有效签名的用户插件，包括早期没有签名的 `version:1` 记录；需要在界面重新审查并批准。
- 启用时再次计算哈希，若与界面展示的哈希不同，返回 `409 / PLUGIN_PACKAGE_CHANGED`，必须刷新后重新确认。
- 启动时也校验哈希；批准后文件变化，插件不会自动导入，持久化启用状态会被重置为 `false`。
- 若本进程已经导入过该插件，随后包发生变化，不能直接热替换。返回 `409 / PLUGIN_RESTART_REQUIRED`：**先重启服务，再刷新列表并批准新内容**。这是为了避免 Node ESM 缓存混用新入口和旧依赖。
- 禁止覆盖已安装目录；ZIP 升级需先禁用、备份插件数据并卸载旧包，安装新包，然后重启、重新批准。不要把可变运行数据写入插件包目录，建议使用 `configs/` 下独立的数据文件，否则下一次加载会因内容变化而要求重新批准。

哈希只是批准内容的标识；服务器签名只证明本服务签发过该批准，**不是代码安全审查、第三方发行者签名或持续运行时完整性防护**。主服务源码、插件目录以外的依赖以及批准记录本身仍属于可信部署。拥有主机写权限或已经获得执行授权的恶意插件，可以绕过应用内检查；不能把本机制当作入侵后的恢复保障。更改磁盘文件不会自动卸载内存中的旧代码，更新时应停用并重启。

## API 示例

先用管理员会话请求 `GET /api/plugins`，取得目标用户插件的 `packageHash`，再确认授权：

```http
POST /api/plugins/my-plugin/toggle
Authorization: Bearer <admin-session-token>
Content-Type: application/json

{"enabled":true,"password":"<current-admin-password>","trust":true,"packageHash":"<SHA-256 from plugin list>"}
```

密码正确但未提供 `trust:true` 或哈希，返回 `403 / PLUGIN_TRUST_REQUIRED`；旧批准缺失时不能直接调用加载器绕过批准。内置插件的启用只要求管理员会话和当前密码，不需要用户插件的 `trust/packageHash` 字段。

## 保留的认证与安装修复

- token 只接受服务签发的 64 位十六进制字符串，只查自有键，且要求 `expiryTime` 为有限数字并未过期。`constructor`、`__proto__` 和损坏记录一律拒绝。
- 管理 API 的认证在静态文件和插件路由分派之前执行；`UI_ENABLED=false` 不改变认证要求。启用二次认证与登录共用频率限制和锁定。
- 插件配置读取、格式校验或持久化失败时，终止插件启动/初始化，不再用空配置把禁用插件变成默认启用。
- 插件私有路由及其直接调用入口都需管理员会话。只有可信内置插件在自身命名空间显式声明 `public:true` 才能跳过主路由的管理员认证；用户插件的 `public:true` 不会自动免认证。唯一经过审查的旧路径兼容例外是 Potluck 的 `/api/potluckuser`：它仍使用用户自己的 `maki_` Key 鉴权，缺失或错误 Key 返回 401。相邻 `/api/potluck/*` 管理端仍要求管理员会话，且复用统一的 token 校验器。插件作者不应自行绕过这些认证流程。
- 安装先在临时目录完整校验解压，再发布；保留路径穿越、重复路径、解压大小、条目数限制以及覆盖保护。

## 相关配置接口的保护

- 提示词编辑/读取仅允许项目目录内、应用代码目录和私有目录之外的 `.txt` / `.md` 文件；拒绝链接、硬链接、路径越界，以及对 JSON、密码文件、插件源码或私有密钥的覆盖。也检查未在请求中重新提交的旧提示词路径。非法路径在修改任何配置之前返回 403；正常文本编辑保留，写入失败不再返回成功。
- 提供商池文件选择器仅允许独立的 JSON 数据文件，不能指向私有密钥、代码或主配置、插件批准、会话等控制文件。
- 修改管理员密码现在必须提交 `currentPassword`。两个前端改密入口均提供当前密码输入，避免仅靠会话先重设密码、再绕过插件启用确认。
- 通用配置查看、下载、删除及备份接口不再暴露或操作 `configs/pwd`、`configs/token-store.json`，也不跟随链接访问私有目录。普通提供商凭据备份保留；管理员密码、会话和 `.private/` 不属于在线配置 ZIP 备份，需要管理员在主机上单独安全保管。

## 回归验证

```sh
npm run test:security
npm test -- --runInBand --testPathIgnorePatterns=api-integration
```

安全测试在临时目录中运行真实 HTTP 服务和重启子进程，不修改现有密码、token 或插件配置，也不调用外部模型。覆盖未授权访问、原型 token、上传不执行、明确批准后的正常 Node 能力、路由/中间件/钩子、批准签名持久化与重启、依赖篡改和重新批准、初始化失败回滚及密码锁定，以及磁盘写失败、损坏配置、真实 Potluck 用户/管理端、配置写入绕过、签名伪造、敏感文件备份和改密二次确认。升级专项测试还使用真实 tar.gz、本地 Git 仓库和重启子进程，覆盖私有状态保留、首次迁移和复制失败恢复；下载被模拟，不访问真实发布源。

## 已发生利用时

本补丁不能撤销已有后门或泄露。停止旧进程，从可信版本重新部署，检查插件目录、静态目录及启动持久化项，撤销管理员会话，并轮换可能泄露的 API key、OAuth 凭据和管理员密码。不要只修改 `enabled` 或热更新文件后继续信任原进程。
