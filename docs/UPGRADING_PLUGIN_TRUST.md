# 重大变更升级指南：可信插件批准与本机签名密钥

> [!WARNING]
> **这是有迁移要求的安全变更，不是无感升级。** 适用于首次升级到包含“管理员批准 + 包哈希 + 服务器签名”的版本；包含本次改动的版本发布时，应将本指南作为破坏性变更列入发行说明。
>
> 老用户插件的 `enabled:true` 不会被自动转换为信任批准。升级后请预留管理员重新审查、启用插件的时间；依赖这些插件的功能在重新批准前可能不可用。不要为免除迁移而恢复旧认证漏洞或自动批准历史文件。

完整信任模型及 API 说明见 [PLUGIN_SECURITY.md](./PLUGIN_SECURITY.md)。插件批准后拥有服务进程权限，不是运行在安全沙箱中。

## 1. 哪些用户受影响

| 场景 | 升级后的行为 | 必须做的事 |
| --- | --- | --- |
| 不使用用户插件 | 不需要生成插件签名密钥 | 正常升级，留意下方其他管理接口变更 |
| 历史用户插件仅有 `enabled:true` 或无签名的 v1 批准 | 禁用并将 `enabled:false` 写回配置；不导入代码 | 登录插件页，审查后再次输入密码、确认信任并启用 |
| 已有有效 v2 签名，包、批准记录和本机密钥均保留 | 后续正常升级/重启仍可自动加载 | 一并保留三个组成部分，无需每次升级重新批准 |
| Docker 只保存 `configs/`，没有保存 `.private/` | 容器重建后旧批准可能失效 | 重建前迁出旧密钥，并补充持久化挂载 |
| 应用目录只读，且没有可写的 `.private/` 挂载 | 第一次批准时不能创建密钥，插件无法启用 | 为服务账号提供独立可写、持久的私有状态目录挂载 |
| 密钥丢失、损坏、被替换，或插件文件变化 | 不接受旧批准，不自动换密钥继续加载 | 恢复匹配的可信备份，或重新审查批准 |

**这把密钥不会替换管理员登录密码、客户端 API Key 或供应商 OAuth 凭据。** 它只用来验证本实例签发的用户插件批准记录；但插件被禁用会影响其提供的业务功能。

## 2. 升级前：停服并备份完整状态

在可信主机上停止服务后，安全备份以下内容：

1. `configs/`：包括插件批准记录 `configs/plugins.json` 和原管理员密码文件。
2. **`.private/`（如果已存在）**：其中 `.private/plugin-approval.key` 是本实例的签名密钥。
3. 用户插件包：本地运行通常为 `src/plugins-user/`；Docker 中为 `/app/src/plugins-user`，宿主机目录以实际挂载为准。

尽量对同一停服时点的数据做配套备份。密钥、批准记录和实际插件包必须匹配；只恢复 `plugins.json` 不能恢复批准。

- **在线“下载所有配置”ZIP 不等于完整灾备**：它不包含 `.private/`；新版还明确排除管理员密码和登录会话。无论来自哪个旧版本，都不能用它代替上述主机侧配套备份。
- 不要把密钥放进插件 ZIP、Git、镜像、公共对象存储或公开问题截图；需要加密备份并限制访问权限。
- 首次从旧版升级时没有 `.private/` 是正常情况。不必预先手工编造密钥，也不要复制其他实例的密钥。
- 服务从其工作目录定位 `.private/`。改用另一部署目录时，必须一并迁移私有状态，并保持正确工作目录。

## 3. Docker / Compose 用户

### 3.1 补充第三个持久化目录

除原有配置和插件目录外，还需保留容器内 `/app/.private`：

```yaml
services:
  aiclient-api:
    volumes:
      - ./configs:/app/configs
      - ./plugins:/app/src/plugins-user
      - ./.private:/app/.private
```

这是示例，不要机械替换现有宿主机数据路径。Compose 相对路径按 Compose 文件位置解析；项目提供的默认文件使用 `./`，build/dev 文件使用 `../`。升级前运行 `docker compose config` 确认三个挂载都指向原有数据所在位置。

`docker run` 部署增加：

```text
-v "你的持久化路径/.private:/app/.private"
```

仅执行 `docker pull`、更新镜像或保留旧 Compose 文件，不会自动为旧容器增加挂载。新建的空目录也不会自动包含旧容器里的密钥。

### 3.2 已经批准过插件，但旧容器未挂载 `.private/`

**不要先删除旧容器。** 停止后，从旧容器复制现有私有状态到计划挂载的宿主机目录，例如：

```bash
docker stop aiclient2api
mkdir -p /srv/aiclient2api/.private
docker cp aiclient2api:/app/.private/. /srv/aiclient2api/.private/
```

只在旧容器确实已有私有状态时执行复制。确认成功并安全备份后，再配置挂载、更新镜像并重建容器。示例中的目录必须替换为真实路径；运行服务的账号需有读写权限。不要使用 `chmod 777` 解决权限问题。

若来自从未生成密钥的旧版本，可直接准备新的持久化目录，在升级后第一次明确批准插件时由服务自动生成密钥。

### 3.3 重建与验证

在正确的 Compose 项目目录更新配置后，再执行：

```bash
docker compose pull
docker compose up -d --force-recreate
```

源码构建部署则使用对应的 Compose 文件和 `up -d --build`。不要把 `down -v`、清理数据卷或删除宿主机状态目录当成常规升级步骤。其他容器编排同样需要持久卷，而不是容器临时层或随重建消失的临时目录。

`.private/` 必须是实际可访问的目录，密钥必须是普通文件；密钥文件及目录不能通过软链接/硬链接代替。只读、以链接形式投影的 Secret/ConfigMap 挂载不适用于这一自动生成、持久化密钥的路径。

若多副本共享同一份 `configs/plugins.json` 和插件包，也必须使用配套的同一逻辑实例密钥；各自生成不同密钥会互相判定批准无效。当前批准流程的文件锁是进程内锁，**没有跨实例并发审批保证**，请采用单实例/单写者管理，不要把这次改动视为新增多副本支持。独立部署则不要混用密钥。

此处是部署要求；自动化测试不等于对所有 Docker、文件共享和权限配置都完成了实际验证。

## 4. 本地 Git / 在线 tarball 更新

- Git 部署中的 `.private/` 是被忽略的本机状态，不应成为被跟踪的源码。**新版内置 Git 升级器在 stash/checkout 之前检查目标 tag；若目标根目录跟踪 `.private` 或其大小写别名，直接拒绝该版本**，避免 Git 覆盖本机原本被忽略的密钥。手工 Git 操作不自动享有此检查；不要自行使用清除忽略文件的命令（例如 `git clean -fdx`），也不要只迁移仓库内被 Git 跟踪的文件。
- **新版 tarball 升级器将 `.private/` 列为保留目录**，连同 `configs/` 保留；即使升级包意外包含 `.private` 或大小写变体，也不会把包内密钥安装到本机或替换已有密钥。
- 升级器不代替管理员批准历史插件，也不会为了升级自动生成或轮换密钥。
- 首次从旧版跨越此变更时，执行更新动作的仍可能是**旧版升级器**。新保留规则不会追溯保护已经开始的旧升级过程，首次升级必须先完成备份和持久化检查。
- tarball 更新会重建主程序目录，并备份/恢复用户插件目录。失败恢复路径会尝试恢复用户插件，私有目录不会被替换；**这不是整个应用代码的原子回滚保证**。若代码复制失败，应停止服务、检查日志并恢复可信完整代码，不要直接运行半更新目录。

## 5. 升级后：首次批准与正常重启

1. 启动服务并重新加载管理页面，避免旧前端缺少新请求字段。
2. 进入插件页。历史无有效签名的用户插件显示需要批准，且不会在展示列表时执行入口代码。
3. 核对来源、文件内容和 SHA-256，确认其拥有服务进程权限的风险。
4. 勾选信任并输入当前管理员密码，再启用插件。服务自动创建本机密钥（如尚未存在），初始化成功后保存 v2 签名批准记录。
5. 确认插件路由、钩子等业务功能正常；在持久化配置确认无误后做一次正常重启验证。

如果插件包和本机密钥未变化且保持启用，后续重启不需再次确认。不要手工把 `enabled` 改回 `true` 来代替批准；早期无签名记录不会因此生效。

升级后若包变更且当前进程已经导入过它，会返回 `PLUGIN_RESTART_REQUIRED`。先停服/重启，再刷新列表批准新内容，避免 Node 依赖缓存混用新旧代码。可变运行数据应放在包目录之外，否则下次加载会因哈希变化而需要重新批准。

## 6. 故障恢复

| 症状 | 处理方式 |
| --- | --- |
| 历史插件升级后变成禁用 | 这是预期迁移；审查后在插件页重新批准 |
| 插件首次启用失败，日志出现私有目录权限错误 | 检查工作目录、`.private/` 挂载和服务账号权限；不应关闭校验或开放所有目录权限 |
| 密钥丢失 | 停服并恢复原密钥及匹配记录/包；没有可信备份则重新审查批准，生成新密钥 |
| 密钥文件损坏或格式错误 | 先停服，在主机上恢复原文件；或将损坏文件移走留作排查，再重新批准。服务不会静默覆盖损坏密钥 |
| 恢复密钥后插件仍是禁用 | 之前的校验失败可能已持久化 `enabled:false`；恢复密钥不会自动翻回启用，仍需管理员明确启用 |
| 插件文件变化 | 审查新包，必要时重启后重新批准，不要篡改哈希或签名 |
| 插件配置损坏、只读或磁盘写满，启动/初始化中止 | 修复配置、权限或空间，再重启；失败时不会用空配置默认启用插件 |

更换密钥会让其他旧签名也失效，不是只影响当前点击的插件。不要删除整个 `.private/` 来尝试“修复升级”，也不要从升级包或其他独立实例取一把已知密钥。

如果必须回退版本，先停服并保留升级前后的配套备份，恢复可信完整代码与相应状态；不要假设只回退代码就会恢复插件启用标志。**不建议回到已知存在认证绕过的旧版**；若此前已被利用，升级或恢复旧备份并不能证明后门已清除，需按 [安全说明](./PLUGIN_SECURITY.md#已发生利用时) 处理。

## 7. 同批其他兼容性变更

- 修改管理员密码的 API 需提交 `currentPassword`，旧前端/自动化客户端应更新。
- 提示词文件编辑仅允许安全位置的 `.txt` / `.md`，不能再把该功能当作通用 JSON 或代码文件编辑器。
- 通用配置查看、下载、删除和在线备份排除管理员密码及会话存储；普通供应商配置备份保留。
- 用户插件的管理/私有 API 需要管理员会话。旧页面若直接调用 `fetch('/api/...')` 会收到 401，需改用 `/app/plugin-page-api.js`；详细迁移和排查步骤见 [自定义插件管理页面鉴权迁移指南](./PLUGIN_PAGE_AUTH_MIGRATION.md)。Potluck 的独立用户用量接口保留其自身 API Key 鉴权。
- 修改插件 HTML/JS 会改变包哈希；当前进程已加载旧包时需先重启，再重新批准新哈希。不要通过重新开放插件路由来恢复旧页面。

## 8. 回归验证范围

运行 `npm run test:security`。`tests/security/plugin-upgrade.test.mjs` 使用临时应用、真实 tar.gz、真实本地 Git 仓库及重启子进程，模拟下载响应，不访问真实发布源，不修改生产配置：

- tarball 包含 `.private` / `.PRIVATE` 时仍保留原密钥、批准记录及用户插件；升级后批准可验证并可重启加载。
- 首次升级不导入升级包里的密钥，不自动批准旧的 `enabled:true` 插件。
- 复制失败时私有状态保持不变，并恢复备份的用户插件目录。
- 正常 Git 更新保留本机私有状态；若目标 tag 意外跟踪私有目录，在 checkout 前拒绝，原密钥及 HEAD 保持不变。
- 三种语言 README 的 Docker 命令和各 Compose 示例包含 `.private/` 挂载，并链接到本迁移指南和插件页面鉴权迁移指南。

缺少 Git/tar 可执行文件的环境会明确跳过对应测试；Docker 数据卷重建等部署行为仍需在实际部署环境验收。
