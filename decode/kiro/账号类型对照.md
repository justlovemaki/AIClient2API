# 三类账号的接口差异（AWS Builder ID / 社交账号 / 企业账号）

> 结论先说：**同一个 `kiro-cli`，三类账号走三套完全不同的认证协议，落到不同的 token 类型，触发不同的接口子集。** 之前我写的是一条通用路径，这里按账号类型拆开。

## 0. 三类是谁，怎么登录

| 账号类型 | 本质 | 登录命令 | 计费/许可 |
|---|---|---|---|
| **AWS Builder ID**（AWS 号） | AWS SSO-OIDC 公共身份池，个人免费号 | `kiro-cli login --license free` | Free tier |
| **社交账号**（Google / GitHub） | Kiro 自有 OAuth，`app.kiro.dev` 门户 | `kiro-cli login --social google` / `--social github` | Free tier（社交登录默认） |
| **企业账号**（Identity Center / 外部 IdP） | AWS IAM Identity Center + 企业 IdP（Okta/Azure AD 等） | `kiro-cli login --license pro --identity-provider <start-url> --region <region>` | Pro / 企业订阅 |

`--use-device-flow` 是三类都通用的开关：强制走设备码，不弹浏览器。

## 1. 认证协议差异（核心）

| | AWS Builder ID | 社交账号 | 企业账号 |
|---|---|---|---|
| 协议 | **AWS SSO-OIDC**（标准三连） | **Kiro 自有 OAuth + PKCE** | **SSO-OIDC + 企业 IdP 中转** |
| 发现端点 | `POST https://oidc.{region}.amazonaws.com/client/register` | `https://app.kiro.dev/signin?state=` | 同 Builder ID，但 start-url 指向企业门户 |
| 授权端点 | `POST .../device_authorization` | `POST https://prod.us-east-1.auth.desktop.kiro.dev/oauth/device/authorization` | `.../device_authorization`（authority = 企业 IdC） |
| 换 token | `POST .../token` | `POST .../oauth/device/poll` 轮询 | `POST .../token` |
| 人工确认页 | `https://portal.sso.{region}.amazonaws.com`、`https://view.awsapps.com` | `https://app.kiro.dev/...` | 企业自己的 IdP 登录页（Okta/Azure） |
| 本地回调 | 无（纯设备码） | `http://localhost:3128/oauth/callback` | 无（纯设备码） |
| 客户端注册 | **需要**，`DeviceRegistration` 缓存进 keychain | 不需要（固定 client_id） | 需要，同 Builder ID |
| 额外参数 | `scopes` | `code_challenge` / `code_verifier`（S256） | `idc_region`、`external_idp_region`、`instance_arn`、`oidc_client_id` |

二进制证据：
- `DeviceRegistration`（6 字段）+ 日志串 `Failed to read device registration from keychain` / `Invalid scopes in device registration, ignoring`（`auth/builder_id.rs:196/217/693`）→ 只有 SSO 类账号走"注册客户端"。
- `DeviceAuthorizationResponse{deviceCode, verificationUri, verificationUriComplete, expiresInMilliseconds, intervalInMilliseconds}` → 设备码轮询模型。
- 企业专属字段簇 `RawSettings{ idc_start_url, idc_region, external_idp_domain, external_idp_start_url, external_idp_region, signin_help_url, auth_portal_url }`。
- `ExternalIdpToken`（8 字段）vs `SocialToken`（`accessToken, expiresIn, profileArn, authMethod`）。
- `kiro-cli profile` 的帮助文本：**"Show the profile associated with this idc user"** —— 这条子命令只对 IdC 账号有意义。

## 2. Token 与请求头差异

三类账号最终都发 `authorization: Bearer <token>`，但 token 来源和 `tokentype` 头不同：

| | AWS Builder ID | 社交账号 | 企业账号 | API Key（补充） |
|---|---|---|---|---|
| token 存储 | keychain `kirocli:auth:*` | keychain 独立条目 | keychain 独立条目 | 环境变量 `KIRO_API_KEY` |
| `tokentype` 头 | 推断 `BUILDER_ID` ⚠️ | 推断 `SOCIAL` ⚠️ | 推断 `EXTERNAL_IDP` ⚠️ | **实测 `API_KEY`** ✅ |
| 刷新机制 | OIDC refresh_token | `forceRefresh` + `expiresAt` | refresh_token + 企业策略可能强制重登 | 无（无过期概念） |
| 账号粒度 | 1 个 AWS Builder ID | 1 个 Google/GitHub 身份 | 1 个 IdC 用户 → 可挂多个 profile | 1 个 key → 1 个 profile |

`tokentype` 的枚举在二进制里只露出三个值：`API_KEY`、`EXTERNAL_IDP`、以及 `CannotParseTokenType` 兜底（`TokenTypeInterceptor`）。`API_KEY` 是实测确认；另两个是枚举里真实存在的字符串，但对应到哪类账号是推断——要实测需要真账号。

## 3. profile ARN 与 region 推导

三类账号的 `profileArn` 形态相同，但**语义不同**：

```
arn:aws:codewhisperer:<region>:<account-id>:profile/<profile-name>
```

| | AWS Builder ID | 社交账号 | 企业账号 |
|---|---|---|---|
| `account-id` | AWS Builder ID 所属账号 | Kiro 托管账号 | **企业 IdC 实例所在账号** |
| `profile-name` | 默认个人 profile | 个人 profile | 企业分配的 profile（可能多个） |
| 数量 | 1 | 1 | 多个，需 `ListAvailableProfiles` 选择 |
| region 来源 | ARN 第 4 段 | ARN 第 4 段 | ARN 第 4 段 |

region 是从 ARN 里**解析**出来的，不是配置项：`endpoints.rs` 里 `profile.arn.split(':').nth(3)` 取第 4 段匹配 `q.{region}.amazonaws.com`。所以 profile 挂了 region 也会跟着变。

企业账号多 profile 时的选择逻辑（日志串）：
- `Lazily resolved profileArn from list_available_profiles`
- `No profiles available. Your administrator has not granted you access to Kiro.` ← 企业特有：管理员没给你授权
- `Every available profile has device flow sign-in disabled` / `Your organization has disabled device flow sign-in. Use browser sign-in.` ← 企业特有的策略限制

## 4. 业务接口差异（不只是"调不调"）

### 4.1 调用序列

| 接口 | AWS Builder ID | 社交账号 | 企业账号 | API Key |
|---|---|---|---|---|
| `GetProfile` | ✅ | ✅ | ✅ | ✅（必调，实测） |
| `GetUsageLimits` | ✅ | ✅ | ✅ | ✅（实测） |
| `ListAvailableProfiles` | 一般不调 | 一般不调 | ✅ **几乎必调** | 失败时才调 |
| `ListAvailableModels` | ✅ | ✅ | ✅ | ✅（实测） |
| `GetUserPreference` | ✅ | ✅ | ✅ | ❌ 跳过（实测） |
| `SetUserPreference` | 按需 | 按需 | 按需（可能被策略禁写） | ❌ |
| `GetEffectiveEnterpriseManagementResourceWithToken` | ❌ | ❌ | ✅ 企业专属 | ❌ |
| `GenerateAssistantResponse` | ✅ | ✅ | ✅ | ✅ |
| `SendTelemetryEvent` | 通用成员 | 通用成员 | **`kiroEnterpriseTelemetryEvent` 成员** | 通用成员 |

### 4.2 `GetUsageLimits` —— 差异最大，返回结构按档位分叉

请求参数三类一致（`origin` + `isEmailRequired`），企业多 profile 时才需要 `profileArn`。差异全在**返回**：

| 档位 | 返回里的关键结构 | 含义 |
|---|---|---|
| 个人 Free | `usageBreakdownList[{type:"AGENTIC_REQUEST", usageLimit, currentUsage, percentUsed}]`、`freeTrialStatus` / `freeTrialExpiry` | 试用与月度限额 |
| 付费 Pro | `overageCapability:"OVERAGE_CAPABLE"`、`OverageCredit{currentUsage, usageLimit, expiresAt}` | 可超额计费 |
| 企业 | `Bonus{displayName, description, usageLimit, currentUsage, expiresAt}`、团队池（档位枚举含 `POOLING`） | 管理员发放额度 + 共享池 |
| 加购 | `AddOnMetadata{addOns, addOnTotalLimit, addOnTotalUsage, timestamp, currentUsageWithPrecision, usageLimitWithPrecision}` | 买额度包 |

额度单位枚举：`AGENTIC_REQUEST`、`CREDIT`。
档位枚举（二进制原串 `PoolingPowerProProMaxProPlus`）：`POOLING` / `POWER` / `PRO` / `PRO_MAX` / `PRO_PLUS`。

**限制类错误按档位不同**：

| 错误 | 触发账号 |
|---|---|
| `DailyRequestCount` / `MonthlyRequestCount` | 个人 Free（日/月次数上限） |
| `OverageRequestLimitExceeded` | 付费（超额再超限） |
| `CreditConsumptionRateExceeded` | 企业（信用额度消耗过快） |
| `ConversationLimitExceeded` | 通用（会话数上限） |

### 4.3 `GetProfile` —— `identityProvider` 是账号类型的直接判据

| 返回字段 | 差异 |
|---|---|
| `identityProvider` | `BuilderId` / `Github` / `Google` / `Enterprise` / `ExternalIdp` |
| `webToolsEnabled` | Free 账号走"非企业"分支；企业受策略控制 |
| `profileName` / `ideCategory` / `arn` | 三类都有 |
| 缺失时 | `ProfileDoesNotExist`（企业 profile 被回收时） |

实测日志里能直接看到账号类型分支：

```
Non-enterprise user detected, enabling web tools without GetProfile check
No profile ARN available, skipping web_tools check (enabled by default)
```

### 4.4 `ListAvailableProfiles` —— 个人 1 条，企业 N 条

| | 个人 | 企业 |
|---|---|---|
| 条数 | 1 | 多个 |
| 选择逻辑 | 直接用 | `Lazily resolved profileArn from list_available_profiles` |
| 专属错误 | — | `ExceededProfilePerIDCInstanceLimit`、`InsufficientFasPermissions`、`InsufficientNumberOfUsers` |
| 空列表文案 | — | `No profiles available. Your administrator has not granted you access to Kiro.` |

### 4.5 `ListAvailableModels` —— 模型集合与计费倍率按档位不同

| 差异点 | 说明 |
|---|---|
| 模型集合 | 高端模型仅 `PRO_PLUS` / `PRO_MAX` 可见；Free 只有基础模型 |
| `rateMultiplier` | 每模型计费倍率，不同档位扣费不同 |
| 企业合规门控 | `modelConsents` 策略 + `ModelDisclaimer{message, policy}`；未同意 → `ModelNotConsentGated` |
| 回退链 | `modelFallbacks[{sourceModelId, targetModelId}]`、`RefusalFallbackModel`（企业可强制指定） |
| 其他错误 | `NotEligible`（档位不够）、`UnknownConsentModel`、`UnknownFallbackSourceModel` |

### 4.6 `GetUserPreference` / `SetUserPreference` —— 个人可写，企业被策略覆盖

| | 个人 | 企业 |
|---|---|---|
| 配置来源 | 用户自己 | 管理员 `PolicyConfigurationBody{key, policy}` + `/etc/kiro/managed-settings.json` |
| 返回里的来源标记 | `ResolvedConfigurationEntry{key, value, source, compose_behavior}` —— **`source` 直接说明这条配置是谁定的** | 同上，`source` 会是 policy/managed |
| 跳过条件 | — | API Key 直接跳过（实测） |
| 写入结果 | `successfulPreferences` / `errors` | 可能返回 `NotEligible` / `Unchanged` / `KmsAccessDenied` |

企业还能限制**登录方式本身**（`login_controls.rs`）：

```
Sign-in uses the administrator's portal or the default portal.
the restriction was ignored and all methods are available.
```

### 4.7 `GenerateAssistantResponse` —— 线格式相同，差异在门控与配额

请求结构三类一致（`conversationState` / `modelId` / `profileArn`），差异在：

| 差异点 | 个人 | 企业 |
|---|---|---|
| `profileArn` | 可选 | 多 profile 时**必带** |
| 模型授权 | 有额度即可 | 需 `modelConsents` 同意，否则 `ModelNotConsentGated` |
| 定制资源 | — | `UnauthorizedCustomizationResourceAccess`、`FeatureNotSupported` |
| 配额错误 | `DailyRequestCount` / `MonthlyRequestCount` | `CreditConsumptionRateExceeded` |

通用（三类共有）错误：`InsufficientModelCapacity`、`PromptTooLong`、`ContentLengthExceedsThreshold`、`DocumentCountExceeded`、`ImageSizeExceeded`、`InvalidToolConfig`、`DuplicateTool`。

### 4.8 `SendTelemetryEvent` —— 企业有独立事件成员

`telemetryEvent` 这个大 union 里除通用成员（`chatAddMessageEvent`、`userTriggerDecisionEvent`、`metricData` …）之外，还有：

```
kiroEnterpriseTelemetryEvent
```

其内部含 `externalIdentityDetails` / `ssoIdentityDetails`（身份来源），只有企业账号的遥测会用到。

### 4.9 企业账号的本地策略注入

企业不仅改服务端行为，还在**本地**落一个配置文件：

```
/etc/kiro/managed-settings.json
```

优先级链（从高到低，日志实测）：

```
管理员 policy  >  managed-settings.json  >  环境变量（KIRO_AUTH_PORTAL_URL 等）  >  用户 settings
```

日志原文：`default (managed-settings.json rejected)` / `default (AuthPortalUrl policy rejected)` —— 低优先级来源被高优先级覆盖时的提示。

## 5. 功能与错误差异

企业账号会撞到一批**其他账号根本不会遇到**的错误（错误枚举里成组出现，说明是服务端按账号类型返回的）：

| 错误码 | 含义 | 只出现在 |
|---|---|---|
| `InsufficientFasPermissions` | 权限不足（FAS） | 企业 |
| `ExceededProfilePerIDCInstanceLimit` | 单 IdC 实例 profile 超限 | 企业 |
| `IdentityProviderAlreadyTaken` / `IdentityProviderNotSupported` | 企业 IdP 冲突/不支持 | 企业 |
| `InsufficientNumberOfUsers` | 席位数不足 | 企业 |
| `InsufficientS3BucketPermissions` / `InsufficientSecretsManagerPermissions` | 企业配置的桶/密钥权限不足 | 企业 |
| `TagPolicyNoncompliant` / `TooManyTags` / `ResourceNameConflict` | 企业资源标签策略 | 企业 |
| `BuilderIdProTier` | Builder ID 升级 Pro 档 | Builder ID |
| `MaxCreditPacks` / `MaxCreditPurchase` / `MinCreditPurchase` | 加购额度包 | 付费账号 |

另外 `subscriptionInfo.subscriptionTitle` 会直接告诉你档位（`Kiro Free` / `Kiro Pro` / 企业订阅），`overageCapability` 决定能否超额。

## 6. 怎么判断当前是哪种账号

```bash
kiro-cli whoami         # 已登录 → 打印身份；未登录 → "Not logged in"
kiro-cli profile        # 仅 IdC 账号有意义：显示 idc 用户的 profile
kiro-cli diagnostic     # 看 install-method、kas 版本等，不含账号类型
kiro-cli settings list  # 看是否配了 identity-provider / social
```

服务端返回里最直接的判定依据：

| 判据 | 说明 |
|---|---|
| `GetProfile` 返回的 `identityProvider` | `BuilderId` / `Github` / `Google` / `Enterprise` / `ExternalIdp` |
| `GetUsageLimits` 的 `subscriptionInfo.subscriptionTitle` | 档位 |
| `ListAvailableProfiles` 返回数量 > 1 | 基本可判定企业账号 |
| 遥测里的 `codewhispererterminal_authMethod` 维度 | CLI 自己也在按账号类型打点 |

## 7. 按账号类型模拟调用

### 7.1 AWS Builder ID

```bash
# 前置：SSO-OIDC 三连拿 token
curl -sS -X POST "https://oidc.us-east-1.amazonaws.com/client/register" \
  -H 'content-type: application/json' \
  -d '{"clientName":"kiro-cli-3.5.0","clientType":"public","scopes":["codewhisperer:completions","codewhisperer:analysis"]}'
# → clientId / clientSecret，缓存起来（对应 DeviceRegistration）

curl -sS -X POST "https://oidc.us-east-1.amazonaws.com/device_authorization" \
  -H 'content-type: application/json' \
  -d '{"clientId":"<cid>","clientSecret":"<csec>","startUrl":"https://view.awsapps.com/start"}'

curl -sS -X POST "https://oidc.us-east-1.amazonaws.com/token" \
  -H 'content-type: application/json' \
  -d '{"clientId":"<cid>","clientSecret":"<csec>","deviceCode":"<dc>","grantType":"urn:ietf:params:oauth:grant-type:device_code"}'

export KIRO_TOKEN='<accessToken>'
```

### 7.2 社交账号（Google / GitHub）

```bash
# 1) 发起
curl -sS -X POST "https://prod.us-east-1.auth.desktop.kiro.dev/oauth/device/authorization" \
  -H 'content-type: application/json' \
  -d '{"client_id":"kiro-cli","scope":"openid profile email offline_access","provider":"github"}'
# → deviceCode / verificationUri / intervalInMilliseconds

# 2) 轮询（间隔按 intervalInMilliseconds）
curl -sS -X POST "https://prod.us-east-1.auth.desktop.kiro.dev/oauth/device/poll" \
  -H 'content-type: application/json' -d '{"device_code":"<dc>"}'
# → accessToken / refreshToken / expiresIn / profileArn / authMethod
```

浏览器路径则由本地 `http://localhost:3128/oauth/callback` 收 code，再 PKCE 换 token（`code_challenge_method=S256`）。

### 7.3 企业账号（Identity Center）

```bash
kiro-cli login --license pro \
  --identity-provider https://my-company.awsapps.com/start \
  --region us-east-1
```

等价的手工流程：

```bash
# 1) 向企业 IdC 的 OIDC 端点注册 + 设备授权（region 用企业 IdC 所在区）
curl -sS -X POST "https://oidc.us-east-1.amazonaws.com/client/register" -d '{...}'
curl -sS -X POST "https://oidc.us-east-1.amazonaws.com/device_authorization" \
  -d '{"clientId":"<cid>","clientSecret":"<csec>","startUrl":"https://my-company.awsapps.com/start"}'
# 2) 用户在 Okta/Azure 页面确认 → 换 token
curl -sS -X POST "https://oidc.us-east-1.amazonaws.com/token" -d '{"grantType":"...device_code", ...}'
# 3) 列 profile（企业通常多个，必须选）
curl -sS -X POST "$BASE/" -H "x-amz-target: AmazonCodeWhispererService.ListAvailableProfiles" \
  -H "authorization: Bearer $KIRO_TOKEN" -d '{"maxResults":50}'
# 4) 企业策略（仅企业账号）
curl -sS -X POST "$CTRL/" \
  -H "x-amz-target: KiroControlPlaneBearerService.GetEffectiveEnterpriseManagementResourceWithToken" \
  -H "authorization: Bearer $KIRO_TOKEN" \
  -d '{"clientSurface":"CLI","clientVersion":"3.5.0","manifestVersionId":"0.1.0"}'
```

## 8. 证据等级说明

| 结论 | 等级 |
|---|---|
| 三类登录命令与参数（`--license free/pro`、`--social`、`--identity-provider`、`--region`） | **实测**（`kiro-cli login --help` 原文） |
| `tokentype: API_KEY` | **实测**（本地 mock 抓包） |
| 社交账号门户/回调/设备码端点 | **实测**（运行日志打印 host 与端口）+ 字符串 |
| API Key 跳过 `GetUserPreference` | **实测**（日志原文） |
| Builder ID 的 SSO-OIDC 三连 | **字符串**（`/client/register`、`device_authorization`、`/token`、`DeviceRegistration`） |
| 企业专属字段与错误码 | **字符串**（`RawSettings` 字段簇、错误枚举） |
| `tokentype` 在企业/社交下的取值 | **推断**（枚举里有 `EXTERNAL_IDP`，未实测到具体映射） |
| 企业账号必调 `ListAvailableProfiles` | **推断**（多 profile 场景的日志串支撑） |
| 档位枚举 `POOLING/POWER/PRO/PRO_MAX/PRO_PLUS` | **字符串**（二进制 `PoolingPowerProProMaxProPlus`） |
| `kiroEnterpriseTelemetryEvent` 为企业专属 | **字符串**（union 成员名 + 内部 `externalIdentityDetails`/`ssoIdentityDetails`） |
| `/etc/kiro/managed-settings.json` 与策略优先级 | **字符串**（`login_controls.rs` 日志文案） |
| `ResolvedConfigurationEntry.source` 标明配置来源 | **字符串**（字段簇 `key/value/source/compose_behavior`） |
| 各档位具体可见模型清单 | **未获取**（需真账号调 `ListAvailableModels`） |
| 企业是否强制 v3/KAS 引擎 | **未知**（无证据） |
